# Shared Refrigerator Management System — Spec

> Implementation specification. Written for a coding agent. Follow the conventions in §3 and §4 exactly; they are not suggestions.
>
> How those rules are applied: [DESIGN.md](DESIGN.md). Accepted product decisions: [adr/](adr/).

------

## 1. Overview

A shared refrigerator management system for a small team. Tracks food items, owners, expiration dates, sharing status, physical placement, per-user item quotas, and per-shelf capacity.

Scope: single refrigerator, ~4 shelves, ~5 users, ~30 food items. Internal tool, no public access.

## 3. Blazor Conventions (mandatory)

These five rules exist because violating them produces silent failures. Apply them without exception.

### 3.1 Render mode: global Interactive Server, prerendering off

In `Components/App.razor`, choose Interactive Server only when the request accepts interactive routing. Account pages stay static SSR (§3.2):

```razor
@using Microsoft.AspNetCore.Components.Web

<HeadOutlet @rendermode="PageRenderMode" />
...
<Routes @rendermode="PageRenderMode" />

@code {
    [CascadingParameter]
    private HttpContext HttpContext { get; set; } = default!;

    private IComponentRenderMode? PageRenderMode =>
        HttpContext.AcceptsInteractiveRouting()
            ? new InteractiveServerRenderMode(prerender: false)
            : null;
}
```

Do **not** add per-page or per-component `@rendermode` directives anywhere else in the app. Do not use `InteractiveAuto` or `InteractiveWebAssembly`. Do not set Interactive Server unconditionally on `Routes` — that would make Account pages interactive and break their POST handlers.

`App.razor` may use the cascading `HttpContext` **only** to choose this render mode. Interactive pages still follow §3.4.

### 3.2 The Account folder stays static SSR

`Components/Account/**` is generated by the template and must remain non-interactive. It already carries `[ExcludeFromInteractiveRouting]` via its `_Imports.razor`. Do not remove that attribute, do not add `@rendermode` to those components, and do not move login/logout POST handlers, Identity endpoint mapping, or Identity service registration out of them.

Shared pure helpers that Account and the rest of the app both need (local-URL sanitisation, upload-path checks) may live in `Services/`. Markup and `fm-*` styles on Account pages may change.

### 3.3 DbContext: always via `IDbContextFactory`

Register in `Program.cs`:

```csharp
var cs = builder.Configuration.GetConnectionString("DefaultConnection");

builder.Services.AddDbContextFactory<AppDbContext>(opt => opt.UseNpgsql(cs));

// Identity requires a scoped DbContext; resolve it from the factory.
builder.Services.AddScoped<AppDbContext>(sp =>
    sp.GetRequiredService<IDbContextFactory<AppDbContext>>().CreateDbContext());
```

Delete the template's `AddDbContext<ApplicationDbContext>` call. Do not register both `AddDbContext` and `AddDbContextFactory` with default options lifetimes — they conflict.

In every service method:

```csharp
await using var db = await _factory.CreateDbContextAsync();
```

Never inject `AppDbContext` directly into a `.razor` component. Never hold a `DbContext` in a field.

### 3.4 Current user: `AuthenticationStateProvider`, never `HttpContext`

There is no `HttpContext` inside an interactive circuit. Do not inject `IHttpContextAccessor`. Account pages (static SSR) and `App.razor` (§3.1) may use the cascading `HttpContext`; interactive pages and services must not.

In components, use the cascading authentication state:

```razor
[CascadingParameter]
private Task<AuthenticationState> AuthState { get; set; } = default!;

private async Task<ClaimsPrincipal> GetUserAsync()
    => (await AuthState).User;
```

Service methods that need identity take `ClaimsPrincipal` as a parameter. They do not resolve it themselves.

### 3.5 Roles must be explicitly enabled

The template's `AddIdentityCore` does not include roles. Update it:

```csharp
builder.Services.AddIdentityCore<ApplicationUser>(options => ...)
    .AddRoles<IdentityRole>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddSignInManager()
    .AddDefaultTokenProviders();
```

Without `AddRoles`, `user.IsInRole("Admin")` and `<AuthorizeView Roles="Admin">` return false with no error.

Register the policy:

```csharp
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
```

## 4. Architecture

```text
.razor component      ← UI, binding, calls services
   ↓
Service               ← business rules, authorization decisions
   ↓
IDbContextFactory     ← per-operation DbContext
   ↓
PostgreSQL
```

Rules:

- **No repository layer.** `DbContext` is already Unit of Work + Repository.
- **No business logic in components.** Components call a service and render the result.
- **No `DbContext` in components.** Components never touch EF Core directly.
- **All authorization decisions live in services.** Components may use `<AuthorizeView>` to hide UI, but the service must independently enforce the rule.

### 4.1 Folder Layout

The live file list (including extension services such as `IImageStorage` and AI analysis) is in [DESIGN.md](DESIGN.md) under **Folders**. Do not maintain a second inventory here.

These constraints stay mandatory:

- Dashboard is `Components/Pages/Home.razor`.
- `Components/Account/**` remains static SSR. Do not remove `[ExcludeFromInteractiveRouting]`, do not add `@rendermode`, and do not move POST handlers or Identity registration out. Shared URL/path helpers may live in `/Services`.
- Pages stay thin: they call services and render. New `fm-*` pages go under `Components/Pages` or `Components/Shared`.

## 5. Domain Model

### 5.1 Enums

```csharp
public enum FoodCategory { Drink, Snack, Meal, Ingredient, Other }
public enum FoodStatus   { Active, Consumed, Missing, Discarded }
public enum ExpiryState  { Normal, ExpiringSoon, Expired }   // computed, never persisted
```

### 5.2 Entities

```csharp
public class ApplicationUser : IdentityUser
{
    public int     ItemQuota  { get; set; } = 5;
    public bool    IsActive   { get; set; } = true;
    public string? TimeZoneId { get; set; }   // null = automatic (browser, then App:DefaultTimeZone)
}

public class Refrigerator
{
    public int    Id   { get; set; }
    public string Name { get; set; } = "";
    public List<Shelf> Shelves { get; set; } = [];
}

public class Shelf
{
    public int    Id             { get; set; }
    public int    RefrigeratorId { get; set; }
    public string Name           { get; set; } = "";
    public int    CapacityUnits  { get; set; }
    public int    SortOrder      { get; set; }
    public Refrigerator Refrigerator { get; set; } = default!;
    public List<FoodItem> Items      { get; set; } = [];
}

public class FoodItem
{
    public int          Id             { get; set; }
    public string       Name           { get; set; } = "";
    public string       OwnerId        { get; set; } = "";
    public FoodCategory Category       { get; set; }
    public DateOnly     ExpirationDate { get; set; }
    public int          SizeUnits      { get; set; }   // 1 / 2 / 3
    public bool         IsShared       { get; set; }
    public FoodStatus   Status         { get; set; } = FoodStatus.Active;
    public int          ShelfId        { get; set; }
    public string?      PositionNote   { get; set; }
    public string?      Note           { get; set; }
    public string?      ImagePath      { get; set; }
    public DateTime     CreatedAt      { get; set; }   // UTC
    public DateTime     UpdatedAt      { get; set; }   // UTC

    public ApplicationUser Owner { get; set; } = default!;
    public Shelf           Shelf { get; set; } = default!;
}
```

### 5.3 Type Rules

- `ExpirationDate` is `DateOnly` → maps to PostgreSQL `date`.
- `CreatedAt` / `UpdatedAt` are always assigned `DateTime.UtcNow`. Npgsql rejects `DateTime` values whose `Kind` is `Local` or `Unspecified`.
- Enums are stored as strings: `.HasConversion<string>()` in `OnModelCreating`.

### 5.4 Indexes

```csharp
entity.HasIndex(f => f.Status);
entity.HasIndex(f => f.ShelfId);
entity.HasIndex(f => f.OwnerId);
```

### 5.5 Relationships

```text
Refrigerator    1 ─── N Shelf
ApplicationUser 1 ─── N FoodItem   (Restrict on delete)
Shelf           1 ─── N FoodItem   (Restrict on delete)
```

## 6. Business Rules

### 6.1 Size Units

Physical volume is not modelled. Each item declares a size:

```text
Small = 1, Medium = 2, Large = 3
```

### 6.2 Capacity

Only items with `Status == Active` consume capacity.

```text
ShelfUsage(shelf)     = sum(SizeUnits) where ShelfId = shelf and Status = Active
ShelfRemaining(shelf) = shelf.CapacityUnits - ShelfUsage(shelf)
UserUsage(user)       = count(items) where OwnerId = user and Status = Active
```

### 6.3 Creation Guards

Both must pass before an item is created:

1. **User quota** — `UserUsage(owner) < owner.ItemQuota`
2. **Shelf capacity** — `ShelfRemaining(shelf) >= item.SizeUnits`

On failure, reject and return a specific message, e.g.:

```text
"Shelf A has 2 units remaining; this item requires 3 units."
"You have reached your limit of 5 active items."
```

On **edit**, re-check shelf capacity only if the item is still `Active` and `ShelfId` or `SizeUnits` changed. Exclude the item's own current contribution from the sum. Quota is **not** re-checked on edit (an edit cannot add a new active slot).

### 6.4 Expiry State (computed at query time, never stored)

```text
ExpirationDate <  Today             → Expired
ExpirationDate <= Today + 3 days    → ExpiringSoon
otherwise                           → Normal
```

### 6.5 Permissions

| Action | User | Admin |
|---|---|---|
| View any item | ✅ | ✅ |
| Create item | ✅ | ✅ |
| Edit own item | ✅ | ✅ |
| Edit others' item | ❌ | ✅ |
| Change own item status | ✅ | ✅ |
| Change others' item status | ❌ | ✅ |
| Manage users | ❌ | ✅ |

Users are never deleted on any product path — including Identity's "delete personal data" page, which must not delete an account. (The demo seeder may remove a leftover `admin@example.com` that owns no items; that is seed hygiene, not a product delete.) `ApplicationUser.IsActive = false` disables login and circuit revalidation, and omits the member from the dashboard usage table, while preserving their items. Disabled members stay on the admin table so they can be re-enabled, and they stay on the food-list Owner select (labelled `(disabled)`) so their items remain findable. There is no owner picker on create; the owner is always the signed-in user.

Sign-in identifier is **email**. `UserName` stays unique in Identity and is the display name; it is not a sign-in identifier.

### 6.6 Status transitions

`FoodStatus` is one-way after the item leaves the fridge:

```text
Active → Consumed | Missing | Discarded
```

`ChangeStatusAsync` is idempotent when the requested status equals the current status. Changing a non-`Active` item to `Active` is rejected; do not re-run quota or capacity guards to allow reactivation. The detail page never offers a reactivate action. Status buttons are hidden when the item is not `Active`.

## 7. Services

### 7.1 Result Types

```csharp
public record OperationResult(bool Success, string? Error)
{
    public static OperationResult Ok()            => new(true, null);
    public static OperationResult Fail(string e)  => new(false, e);
}

public record OperationResult<T>(bool Success, T? Value, string? Error)
{
    public static OperationResult<T> Ok(T v)          => new(true, v, null);
    public static OperationResult<T> Fail(string e)   => new(false, default, e);
}
```

Services never throw for expected rule violations. They return `Fail` with a user-facing message.

### 7.2 IInventoryService

```csharp
Task<List<FoodItem>>             GetItemsAsync(FoodFilter filter);
Task<FoodItem?>                  GetItemAsync(int id);
Task<OperationResult<FoodItem>>  CreateItemAsync(FoodItemForm form, ClaimsPrincipal user);
Task<OperationResult>            UpdateItemAsync(int id, FoodItemForm form, ClaimsPrincipal user);
Task<OperationResult>            ChangeStatusAsync(int id, FoodStatus status, ClaimsPrincipal user);
Task<OperationResult<string>>    SaveImageAsync(IBrowserFile file, ClaimsPrincipal user);
Task                             DeleteImageAsync(string? imagePath);
```

`CreateItemAsync` and `UpdateItemAsync` enforce §6.3. `UpdateItemAsync` and `ChangeStatusAsync` enforce §6.5 and §6.6. `SaveImageAsync` requires a signed-in caller (§3.4 / §4).

### 7.3 ICapacityService

```csharp
Task<int>                    GetShelfUsageAsync(int shelfId);
Task<int>                    GetShelfRemainingAsync(int shelfId);
Task<int>                    GetUserUsageAsync(string userId);
Task<List<ShelfUsageDto>>    GetAllShelfUsageAsync();
Task<List<UserUsageDto>>     GetAllUserUsageAsync();
Task<DashboardStats>         GetDashboardStatsAsync(DateOnly today);
```

`GetDashboardStatsAsync` returns all dashboard numbers in a single call. Do not issue one query per statistic. The caller supplies `today` in the viewer's time zone. Member rows in those stats are **active** users only.

`GetAllUserUsageAsync` returns every member, including disabled ones, and each `UserUsageDto` carries `IsActive`. The food-list Owner select and the create-form allowance panel use this list. Do not reuse it as the dashboard member table.

### 7.4 IUserAdminService

```csharp
Task<OperationResult<List<AdminUserDto>>> GetUsersAsync(ClaimsPrincipal actor);
Task<OperationResult> CreateUserAsync(string userName, string email, string password, int quota, bool isAdmin, ClaimsPrincipal actor);
Task<OperationResult> SetActiveAsync(string userId, bool isActive, ClaimsPrincipal actor);
Task<OperationResult> SetQuotaAsync(string userId, int quota, ClaimsPrincipal actor);
Task<OperationResult> UpdateMemberAsync(string userId, string userName, string email, int quota, ClaimsPrincipal actor);
Task<OperationResult> SetAdminAsync(string userId, bool isAdmin, ClaimsPrincipal actor);
```

`SetQuotaAsync` and `UpdateMemberAsync` reject a quota lower than the user's current active item count, with an explanatory message. Username and email must stay unique. `SetActiveAsync(false)` and `SetAdminAsync(false)` refuse the actor's own account. `GetUsersAsync` returns `AdminUserDto` so password hashes never reach the UI.

All methods require the `AdminOnly` policy at the page level **and** verify `actor.IsInRole("Admin")` inside the service.

### 7.5 Query Rules

- All filtering happens in the database. Build an `IQueryable`, apply every filter, then `ToListAsync()`.
- Search is a case-insensitive contains on `Name`. Use `ToLower().Contains` after trimming so the same expression translates to both Npgsql and the SQLite test host. Do not use `ILike`.
- Compute date thresholds in C## **before** the query so the expression is translatable. The list page puts the viewer's calendar day on `FoodFilter.Today`; the service falls back to UTC only when that is unset:

```csharp
var today = filter.Today ?? DateOnly.FromDateTime(DateTime.UtcNow);
var soon  = today.AddDays(3);
query = query.Where(f => f.ExpirationDate <= soon && f.ExpirationDate >= today);
```

- Use `.Include(f => f.Owner)` and `.Include(f => f.Shelf)` on list queries. Do not lazy-load.
- Register services as `Scoped`.

## 8. Pages

### 8.1 `/` — Dashboard

Requires authentication. Displays:

- Active item count
- My items (the signed-in user's active count; optional extra stat)
- Expiring-soon count (Active items only)
- Expired count (Active items only)
- Overall refrigerator utilisation (used units / total capacity of Active items, with a progress bar)
- Shared item count (Active items only)
- Per-shelf remaining capacity. A fridge elevation / chip row per shelf is acceptable; a progress bar per shelf is not required
- Per-user current usage (`used / quota`) for **active** members only. Member names deep-link to `/food?owner={userId}`.

Dashboard stat cells and shelf headers may deep-link into `/food?...` using the same filter query as the list.

### 8.2 `/food` — Food List

Card grid. Each card shows: image, name, owner, category, relative expiration, size, shared badge, expiry-state badge. The card may also show the shelf name. Hovering the relative label shows the absolute date.

Relative card labels (`FoodDisplay.ExpiryCardLabel`):

```text
> 1 day ahead   → Expires in {n} days
tomorrow        → Expires tomorrow
today           → Expires today
yesterday       → Expired yesterday
older           → Expired {n} days ago
```

Expiry badge colours: Normal = neutral, ExpiringSoon = warning, Expired = danger.

An owner or Admin may **Discard** an Active expired item from the card. When that Discard control is shown it **replaces** the shared badge on that card (detail still shows both). Discard still goes through `ChangeStatusAsync`. The expired-only restriction is list UX; `ChangeStatusAsync` still allows any Active → Discarded (§6.6).

Filter bar, applied server-side, no submit button:

- All / My items (tab under the page title)
- Search by name (text; debounce 300 ms)
- Shared items (toggle)
- Category (select)
- Shelf (select)
- Owner (select, after Shelf and before Status). Choosing an owner switches the tab back to All. The My items tab clears owner.
- Status (select, defaults to `Active`)
- Expiry state (select: any / Normal / Expiring soon / Expired)
- Clear filters (resets the bar; keeps the All / My items tab and sort)
- Sort (icon + direction toggle next to the item count; field and direction remembered in the browser)

Filter state lives in the `/food?...` query string. Changing a control navigates with `replace: true`. Visiting `/food` without `sort`/`dir` reapplies the browser-stored sort preference. The item-count line is `{matched} of {active} active items` when Status is Active, otherwise `{n} items`.

### 8.3 `/food/{Id:int}` — Food Detail

Displays all fields including `PositionNote` and `Note`. Expiration is the calendar date with a parenthetical day count (`FoodDisplay.ExpirationDetail`), e.g. `6 September 2026 (in 3 days)`, or `(today)` / `(tomorrow)` / `(expired {n} day(s) ago)`. Added and last-updated timestamps use the viewer's time zone.

If the current user is the owner or an Admin, show: **Edit**, **Mark as Consumed**, **Mark as Missing**, **Mark as Discarded**. Status buttons are hidden when the item is not `Active`.

### 8.4 `/food/new` and `/food/{Id:int}/edit` — Food Form

`EditForm` with `DataAnnotationsValidator`. Fields: Name, Category, ExpirationDate, Size, Shared toggle, Shelf, PositionNote, Note, Photo.

Below the shelf selector, show live remaining capacity for the selected shelf. On edit, that figure excludes the item's own current units when the selected shelf is the item's current shelf.

On submit, call the service. If `Success == false`, display `Error` in an alert above the form and keep the entered values.

### 8.5 `/admin/users` — Admin User Management

`@attribute [Authorize(Policy = "AdminOnly")]`

Table of users with: username, email, quota, active item count, status, admin flag. Inline actions: edit username / email / quota, disable/enable, promote or demote Admin (an admin cannot disable themselves or remove their own admin role). Plus a create-user form that can create an administrator.

Disabled members may sit in a separate section of the same page. They must remain visible to an admin so they can be re-enabled.

### 8.6 Image Handling

Card and detail images use a fixed aspect ratio with `object-fit: cover`.

Storage keys, ImageSharp normalisation, provider selection, replacement deletes, and URL resolution are defined in [SPEC_EXTENSIONS.md](SPEC_EXTENSIONS.md) §4. That document supersedes the historical `/uploads/{guid:N}.{jpg|png|webp}` stored-path shape.

Rules that still apply here:

- `InputFile` component, single file
- Accept JPG / PNG / WebP only; do not trust content type or filename alone
- Max 5 MB, enforced via `OpenReadStream(5 * 1024 * 1024)` before buffering
- The client-supplied filename is never used
- `ImagePath` on create/update must be empty or a safe storage key
- If create/update fails after an upload, delete the new object so it is not left behind
- Local `/uploads` is served only to authenticated users; responses set `X-Content-Type-Options: nosniff`

### 8.7 Account / identity

There is no public self-registration. `/Account/Register` and `/Account/RegisterConfirmation` redirect to login and must not create a user or show a confirmation link. Members are created by an administrator at `/admin/users`.

Login is email + password (`[EmailAddress]`). Password sign-in uses lockout (5 failures, 15 minutes). External login may sign in an **existing linked** account only; it must not create an account. Local redirect targets (`ReturnUrl`, logout) must be sanitised to same-origin relative paths.

Profile (`/Account/Manage`) can set a time zone, or leave it on Automatic (browser). `null` `TimeZoneId` means Automatic. The fallback when neither a saved zone nor the browser is available is `App:DefaultTimeZone` (`America/Chicago`).

## 9. Seed Data

Run on startup in development, idempotently.

- 1 refrigerator, 4 shelves with differing `CapacityUnits` (e.g. 20, 20, 15, 10)
- Roles: `Admin`, `User`
- 1 admin (`admin@fridge.local`), 3 users with quotas 10, 8, 3
- `UserName` is the email local-part (`alice`, not `alice@fridge.local`)
- 25–30 food items spanning every category and status, deliberately including:
  - at least 2 already expired
  - at least 3 expiring within 3 days
  - one shelf filled to ≥ 90% capacity
  - one user at their quota limit

The last two make the validation rules demonstrable without setup during a demo.

## 11. Tests

xUnit. Services under test, EF Core with an in-memory SQLite connection.

```text
CreateItem when user is at quota           → Fail, message names the quota
CreateItem when shelf lacks capacity       → Fail, message names remaining units
CreateItem when both pass                  → Ok, item persisted as Active
ChangeStatus to Consumed                   → shelf usage decreases by SizeUnits
ChangeStatus to Consumed                   → user usage decreases by 1
ChangeStatus to Active from non-Active     → Fail (no reactivation)
UpdateItem by non-owner non-admin          → Fail (forbidden)
UpdateItem by admin on another's item      → Ok
UpdateItem when shelf lacks capacity       → Fail, message names remaining units
  (exclude the item's own current units)
ChangeStatus by non-owner non-admin        → Fail (forbidden)
SetQuota below current usage               → Fail
ExpiryState for yesterday                  → Expired
ExpiryState for today + 2                  → ExpiringSoon
ExpiryState for today + 10                 → Normal
```

Image pipeline, AI autofill, and production bootstrap tests are required by [SPEC_EXTENSIONS.md](SPEC_EXTENSIONS.md) §7.1. In that list, “rejected” for an AI field means the field is dropped to `null` with a warning; the analysis result itself still succeeds.

## 12. Error Handling

- Wrap the router in an `ErrorBoundary` with a friendly fallback (recover + link to the dashboard).
- Set `DetailedErrors: true` in `appsettings.Development.json` and on the Interactive Server circuit in Development.
- Expected rule violations surface as `OperationResult.Error` in the UI, never as exceptions.
- Unexpected exceptions are shown as a generic message. The ASP.NET Core host / Blazor Server circuit logs them; the fallback UI does not need its own logger.

## 13. Known Limitations

Document these in the README; do not attempt to fix them.

1. **Capacity check race condition.** The guard and the insert are not in one transaction. Two concurrent creates can both pass and overfill a shelf. Production fix: wrap both in a transaction with a row lock on `Shelf`, or add a `RowVersion` concurrency token with retry.
2. **Interactive Server scaling.** Each user holds a server-side circuit with in-memory state. Horizontal scaling requires sticky sessions or a Redis backplane.
3. **No audit trail.** Status changes are not recorded historically.
4. **Size units are an approximation** and do not reflect real volume.
5. **Disable takes effect on the next revalidation.** After `IsActive = false`, an existing Interactive Server circuit may stay up until security-stamp revalidation (up to 30 minutes). New logins are blocked immediately.
6. **Identity template remnants.** Passkey, 2FA, and Forgot-password pages from the template may remain. They are not product features. External login must not create accounts.

Former items (local-only uploads, orphan files on replacement, missing-file 404, `/uploads/{guid}.ext` path shape) are overridden by [SPEC_EXTENSIONS.md](SPEC_EXTENSIONS.md) §0.1 / §4.
